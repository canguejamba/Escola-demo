## 5.1: Implementazione del login per l'admin e protezione della dashboard

**As an** administrator,
**I want** to log in to the system securely and access a protected dashboard,
**So that** I can manage the website's content without unauthorized access.

### Acceptance Criteria

1.  A new page must be created at `/login` with a form for email and password.
2.  A user must be able to log in using credentials managed by Supabase Auth.
3.  Upon successful login, the user must be redirected to a new `/admin/dashboard` page.
4.  The `/admin/dashboard` page and all other routes under `/admin/*` must be protected.
5.  Unauthenticated users attempting to access `/admin/*` routes must be redirected to the `/login` page.
6.  The dashboard page must display a welcome message and a "Logout" button.
7.  Clicking the "Logout" button must sign the user out and redirect them to the login page.

### Dev Notes

**CRITICAL:** This section contains extracted information from architecture documents. Do not invent or assume technical details not present here.

*   **Previous Story Insights**: This is the first story of a new epic and introduces authentication, a new pattern for the project.

*   **Architecture & Tech Stack**:
    *   Authentication will be handled by **Supabase Auth**.
    *   The application is built with **Next.js**, **React**, and **TypeScript**.
    *   Protected routes will be implemented using **Next.js Middleware**.
    *   [Source: `docs/architettura/1-contesto-e-obiettivi.md`, `docs/architettura/4-flusso-logico-e-coerenza.md`]

*   **File Locations**:
    *   Login page: `pages/login.tsx`.
    *   Dashboard page: `pages/admin/dashboard.tsx`.
    *   Login form component: `src/components/LoginForm.tsx`.
    *   Middleware for protected routes: `middleware.ts` (at the root of `pages` or `src`).
    *   [Source: Standard Next.js project structure.]

*   **Component Specifications**:
    *   **`LoginPage` (`pages/login.tsx`):** Renders the `LoginForm` and handles any login errors.
    *   **`LoginForm` (`src/components/LoginForm.tsx`):** A client component that uses the Supabase client library (`@supabase/auth-helpers-nextjs`) to handle the sign-in logic.
    *   **`DashboardPage` (`pages/admin/dashboard.tsx`):** A simple page that displays a welcome message and a logout button. The logout button should call the Supabase sign-out function.

*   **Authentication Flow**:
    1.  User visits `/admin/dashboard`.
    2.  Next.js Middleware runs, checks for a valid Supabase session cookie.
    3.  If no session is found, the middleware redirects the user to `/login`.
    4.  User submits the login form.
    5.  The form calls the Supabase `signInWithPassword` function.
    6.  Supabase Auth creates a session and sets a cookie.
    7.  The user is redirected to `/admin/dashboard`.
    *   [Source: `docs/architettura/4-flusso-logico-e-coerenza.md`, `docs/architettura/6-vista-logica-componenti-e-relazioni.md`]

*   **Authorization**:
    *   For this story, any authenticated user is considered an admin. Role-based access control (RBAC) is a future concern.
    *   The architecture mentions RLS (Row Level Security) as a key mitigation for data access. While not directly implemented in this story's code, the database should be configured with RLS policies that only allow authenticated users (or specific roles) to perform write operations.
    *   [Source: `docs/architettura/5-rischi-architetturali-e-mitigazioni.md`]

*   **Testing Requirements**:
    *   Unit tests for the `LoginForm` component.
    *   Integration tests for the authentication flow (e.g., testing the middleware redirection).
    *   End-to-end tests for logging in and out.
